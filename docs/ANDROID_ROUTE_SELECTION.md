# Android 快速选路

发送优先使用刷新时已测通的路径，顺序为局域网、公网、中继。手动选路仍沿用原有设置。

## 探测如何并行

- `candidate_routes.dart` 按本地接口和对方候选组成源地址／目标地址对。只排除地址族不匹配、回环、链路本地及明确不可用的接口，不因校园网私网前缀不同就判定不可达。
- 普通接口使用绑定源地址的 Dart HTTPS 探测；蜂窝候选通过 `NetworkBridge.probePeer` 进入 Android，由 `ConnectivityManager` 取得有 Internet 能力的蜂窝 Network，仅绑定本次连接，不改变进程或系统默认网络。
- `RouteProbes` 同时发起候选探测，`ReachabilityMonitor` 的设备检测预算为一秒。探测只交换身份握手和 nonce，不传文件。
- Android 原生探测使用可复用、空闲后回收的线程池，不在两个阻塞任务后排队。文件传输仍使用独立的线程池，文件并发由 Dart 的 `TransferGate` 控制，默认四个。

## 发送如何复用

有效的成功记录保留具体源地址或蜂窝方式。发送可以立即选择该记录，不必再等所有失败地址；某个地址对失败后，仅丢弃这一对，继续使用其他已测通路径。网络、对端候选或证书变化会影响记录有效性。

成功记录先保持局域网／公网的范围优先级，同一范围再按已测延迟排序；延迟相同时优先非蜂窝。关闭蜂窝时仍排除蜂窝。使用缓存时保留这个排序，不让对端原始地址顺序覆盖测量结果。本次两处排序修正的选路相关检查43项通过，尚未安装新包。

一秒是连接选择的共同预算，不是文件传输时限。路径真正建立并开始传输后，不会因超过一秒而切断文件。蜂窝网络从未激活状态恢复、对端离线或系统拒绝连接时，无法承诺一秒内完成真实握手。

## 本次修正与验收状态

原生层原先使用两个固定探测线程；即使 Dart 同时提交请求，前两个地址等待 Network／TLS 时，第三个可达地址仍会被排队。新增 Java 回归先复现这一失败，改用不排队的探测执行器后通过；前两个任务仍保持阻塞时，第三个任务能在一秒等待预算内开始。

入口：`NativeReceiveRuntime.peerProbeExecutor()`。回归：`NativePeerProbeSchedulingTest`。

本修正只在源码，未构建或推送 APK。当前真机仍为 1.0.23+32；Java 调度回归不代替真机蜂窝连通性验收。

## 反向 HTTPS 预检（仅源码）

新增 `ReverseHttpsProbes` 与中心 `httpsPeerProbes` 能力协商：原生接收端先发布监听地址，中心让同组发送端对这些地址做反向 nonce 握手。发送端同时尝试所有符合范围的源接口／目标地址对，公网范围包含已开启的 Android 蜂窝连接。检测不会获取文件票据或打开接收写入器。

手动刷新将内网、公网反向检查与原有地址检查同时发起；定时检查复用 30 秒有效结果。网络、对方候选或证书变化会清空旧缓存并取消正在进行的检测。超时、取消和离线属于未确认，不作为已测失败缓存。

中心协议及相邻发现／文件授权检查 37 项通过，原生模块与既有快速选路检查 19 项通过。当前公网中心未启用此协议，手机仍是原运行包。

尚未完成：将预检结果用于实际文件传输的跨方式就绪调度。当前发送的 HTTPS／反向 HTTPS／RTC 文件授权仍串行。RTC 预检的并行协商已在源码实现，旧设备继续使用单会话方式。不能据此宣称已经实现所有方式在一秒内并行选路。

## RTC 并行预检（仅源码）

中心、原生和 Web 已支持 `rtcParallelProbes` 协商。更新后的设备可以同时检测不同设备及其内网／公网范围；同一设备对、同一范围只保留一个检测会话。旧设备没有声明并行能力时，仍串行与它检测，不改变旧客户端的调用条件。

Web 在同一固定浏览器配置中运行了三个真实 RTCPeerConnection 客户端：共创建并同时持有 12 个连接，三对内网 nonce/echo 在配置启动后 694 ms 全部成功；结束时 12 个连接全部关闭，没有文件传输或历史记录。该结果验证同机浏览器协议与生命周期，不代表手机、iPad 或公网链路的实测延迟。

实际文件发送仍待接入统一就绪调度，不能把预检并行等同于文件写入并行。Android 没有构建或推送新包。
