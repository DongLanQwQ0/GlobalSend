# GlobalSend protocol v1

All API routes are relative to the configured center base URL (including its optional path prefix). Append `/api/v1`. JSON uses camelCase; timestamps are ISO 8601 UTC; sizes/offsets are nonnegative safe integers. Errors: `{error:{code,message}}`. Protected HTTP routes require `Authorization: Bearer <deviceToken>`. Tokens never belong to another center. This center is trusted with plaintext; TLS is transport protection, not E2EE.

## Group passwords and online discovery

- `POST /devices/enroll`: `{groupKey,name,platform}` → 201 `{deviceToken,device,groupId,createdGroup:boolean}`. The wire property remains `groupKey`, meaning **group password**. Same password automatically joins the same group; an unknown password automatically creates one. Minimum 10 characters, maximum 256, exact comparison without normalization or edge whitespace/control characters. There is no entropy check, invitation, pairing step or new-group confirmation. Name is at most 80 characters; platform is `windows|android|web|other`.
- `GET /info` adds `enrollment:{mode:"group-password",groupKey:true,legacyBootstrap:false,pairingCode:false,allowGroupCreation:true,minGroupKeyLength:10}` and optional `discovery:{onlineOnly:true,peerTtlSeconds:1800}`. Old `ALLOW_GROUP_CREATION`, `MAX_GROUPS` and `MAX_DEVICES_PER_GROUP` settings no longer block password enrollment; they are removed from deployment defaults. Passwords are indexed with the existing instance HMAC, not returned in discovery.
- Bootstrap/pairing-code enrollment and `POST /pairing-codes` are retired with `GROUP_PASSWORD_REQUIRED` (410). Bootstrap secret files/environment values are not read. **Already-enrolled device IDs, tokens, group membership and history remain usable**, including v2 migrated identities; reconnect does not require enrollment or an invitation.
- `GET /devices` → `{devices:Device[]}`: only online, non-revoked devices in the authenticated device's group, plus its own identity. Self may be returned offline for settings/reconnect but then has `peer:null,rtc:null`. There is no offline discovery/management list or `includeOffline` mode. Historical transfers/events remain accessible separately.
- Online means at least one authenticated WebSocket. The first connection receives `hello` then broadcasts `presence:true` and `devices.changed`. **Publish peer/RTC metadata only after hello.** An offline caller gets `DEVICE_OFFLINE` (409); refresh may keep the existing two-minute cadence.
- Peer IPv4/IPv6 candidates, current public certificate and RTC capabilities are transient **30-minute online announcements**. New peer data lives only in memory; legacy SQL `peers` rows are cleared at startup. The last socket closing deletes the device's announcements and temporary direct/RTC grants, broadcasts `presence:false` and `devices.changed`, and stops new direct address authorization. Closing one of several sockets does not make the device offline. Reconnect with the same token, receive hello, then republish addresses/capabilities.
- Clients retain a newly offline target for **30 seconds**, with an offline label and sending still available. This is a session-local grace period, not a server presence lease: repeated snapshots do not extend it, reconnect replaces the entry immediately, and old offline history does not receive a fresh grace period on startup. Expiry removes the target; group/center changes clear this cache. Offline devices are not scheduled for online-only probes or new direct/RTC grants. A send may enter the existing center queue for delivery after reconnect; acceptance is not a receipt. This lifecycle does **not** delete historical messages or received/relay files.
- `GET /info` also returns `{protocolVersion:1,instanceId,name,limits,features:{relay:true,direct:true,routePreference:true,directPush:true,rtcDataChannels:true,rtcProbes:true,groupSharedText:true},rtc:{iceServers:[]}}`. Capabilities indicate supported negotiation, not guaranteed physical reachability. All routing, signaling and events remain scoped to the same group.
- `PATCH /devices/me`: `{name}` → `{device:Device}`. Only the current device is renamed; ID, token and history stay unchanged. Notifies same-group clients with `devices.changed`.

Existing administration APIs remain token-authenticated compatibility operations, not enrollment steps: `DELETE /devices/:deviceId` revokes a same-group token and cancels its active transfers; it does not rotate the password or prevent a fresh password-based enrollment. `POST /groups/key {newGroupKey?:string}` retains the stable group and existing tokens while replacing its password; an explicitly changed old password remains retired. Neither operation is needed for ordinary discovery or certificate refresh.

## Text and events

### Shared group editor

`features.groupSharedText=true` enables one persistent plain-text document per group, separate from sent messages and the system clipboard. All current group devices can edit it; joining with the same password or reconnecting fetches the current document. Clearing the field saves an empty document. It does not create transfers, message cards or receipt events.

- `GET /group/shared-text` → `{text,revision,updatedAt,updatedBy,mutationId}`. An unused workspace returns `text:"",revision:0` and empty metadata strings.
- `PUT /group/shared-text`: `{text,baseRevision,mutationId}` → the updated document. Maximum text length is 100000 characters. `mutationId` is a new client ID per edit; retry an unchanged request with the same ID. Repeating the latest committed mutation returns its document without another revision or broadcast.
- A stale `baseRevision` returns 409 `{error:{code:"SHARED_TEXT_CONFLICT",message},current:<document>}`. Clients retain the local draft and offer the remote text or an explicit retry against the latest revision; they must not silently replace concurrent edits. Normal edits debounce for about 400 ms and wait for IME composition to finish.
- Changes broadcast `{type:"sharedText.updated",...document}` to online same-group sockets, including the author. On reconnect, reconcile via GET. The current document is stored in SQLite and survives a center restart; it remains until edited or cleared. It is independent of received-file cleanup.

Clients connected to an older center without this feature retain normal send/receive behavior and do not send shared-editor requests.

- `POST /texts`: `{eventId,targetDeviceId,text}` → 201 `{event:Event,replayed:false}`, repeated identical eventId → 200 `{event:Event,replayed:true}`; conflicting payload → 409. eventId is a client UUID; manual repeat generates a new one. Server derives sourceDeviceId. Target must be a non-revoked same-group device.
- `PATCH /texts/:eventId`: `{text}` → `{event:Event}`. Only the original sender may edit an unexpired message. With `features.textContentSync`, identical manual texts in the same group share `contentId` and a server-incremented `revision`. Editing updates every delivery of that content, while retaining delivery IDs, participants and times. It emits `text.updated` for the affected deliveries; clients replace matching content rather than append another card. Matching another existing text merges the content identities. Automatic clipboard events remain separate. An unchanged edit returns the original event without another revision.
- `GET /texts/latest` → `{documents}` returns the current canonical text and delivery references visible to this participant, including after old notification events expire. Clients reconcile this snapshot on reconnect and ignore older revisions; it does not write the system clipboard.
- `GET /events?after=0&limit=100` → `{events:Event[],cursor:number,hasMore:boolean}`. Cursor is a server integer, persisted across restarts. Only own sent/received events are returned; cursor moves through visible events. Events expire after configured TTL. Expired history is not recovered. Reload transfers separately.
- `POST /events/:eventId/ack`: `{}` → `{ok:true}`; only original target may acknowledge. Emits `text.received` once. HTTP success sending text means accepted by center, not read/copied by peer.
- `POST /session/ws-ticket`: `{}` → `{ticket,expiresAt}` (single-use, 30 seconds).
- `GET /ws?ticket=...` upgrades WebSocket. First message `{type:"hello",deviceId,protocolVersion:1}`. Server pushes `{type:"event",event:Event}` and ephemeral `{type:"presence",deviceId,online}`. Client may send `{type:"ping"}` → `{type:"pong"}`. WS is a notification channel; reconnect always reconciles `/events` and `/transfers`. Native protocol ping/pong keeps liveness. Long-term token never enters URL. Browser Origin must equal configured public base origin (development loopback also allowed only in development).

`Event = {cursor:number,protocolVersion:1,eventId,type,sourceDeviceId,targetDeviceId,createdAt,expiresAt,payload}`. Types:

- `text.created`: payload `{text,clipboard?:{originDeviceId,sourceEventId,parentEventId?}}`. Manual text omits clipboard metadata.
- `text.received`: payload `{sourceEventId}` (source is acknowledging receiver; target is original sender).
- `transfer.offered|transfer.updated`: payload `{transferId,routePreference?:"auto"|"lan"|"public"|"relay"}`; fetch current transfer state. Older events omit routePreference.
- `device.revoked`: payload `{deviceId}`.

### Optional automatic clipboard context (source added, verification paused)

`POST /texts` keeps `{eventId,targetDeviceId,text}` and optionally accepts `clipboard:{sourceEventId?:string}`. First automatic send uses `clipboard:{}`. Center derives payload clipboard `{originDeviceId:authenticatedDeviceId,sourceEventId:eventId}`; clients cannot supply originDeviceId. A forwarded automatic item may reference the **immediate previous text.created eventId visible to this authenticated device**, not an arbitrary root ID. The parent must be unexpired and its text identical; otherwise SOURCE_EVENT_UNAVAILABLE 403 / SOURCE_EVENT_CONFLICT 409. Center propagates its root origin/sourceEventId and adds parentEventId for provenance and stable retry comparison.

Automatic clipboard text is limited to 8192 UTF-8 bytes and retained for `min(global TTL,300 seconds)`. Manual text without clipboard retains the existing global TTL and independent manual-repeat semantics. The authenticated transport sender remains sourceDeviceId even when original clipboard origin differs. Clients suppress re-export of a remote clipboard write using the root pair and platform-local clipboard markers; metadata does not enable background clipboard access or guarantee detection of all sensitive text. No device should mark a text copied merely because the server accepted it.

## Multi-file relay

`Transfer = {transferId,sourceDeviceId,targetDeviceId,createdAt,expiresAt,routePreference,files:TransferFile[]}`. New responses always include routePreference; older responses without it mean auto.
`TransferFile = {fileId,name,size,mimeType,sha256,status,offset,attemptId,errorCode,transport,receiveFailure?}`. `transport` is `null|relay|direct` (direct is selected by the receiver before bytes flow; offset remains center bytes, therefore 0 for direct-only). sha256 is lowercase hex, 64 characters. Allowed file states: `offered|accepted|uploading|ready|received|rejected|canceled|failed|expired`. `offset` is center's committed bytes, not peer saved bytes. Separate files progress/fail independently. Filenames are display metadata, never filesystem paths. Lists max 10000 entries, including directory metadata; each file size is bounded by limits.

### Receiver storage failure and recovery

`features.receiveErrorReporting=true` enables these additive operations:

- Receiver `POST /transfers/:transferId/files/:fileId/receive-error {message}` reports a local destination preparation/write failure (1–500 characters). It sets `status:"failed",receiveFailure:true,errorCode:message` and notifies both participants with `transfer.updated`, so the sender stops waiting. Relay bytes, committed offset, upload attempt and quota reservation remain intact. Completed/canceled/expired entries are not reopened by a late failure report. Route selection timeouts and relay consent prompts are not storage failures.
- Either participant `POST .../receive-retry {}` restores the saved phase and clears this error after the destination is corrected. Relay resumes its existing prefix; a direct connection gets new tickets from `accepted` with no selected transport. Repeating a retry after recovery returns the current file without resetting it. This differs from the source's existing `/retry`, which intentionally starts a new relay upload attempt.
- Cancel/expiry still releases the retained bytes and reservation. An inaccessible old directory does not authorize deleting its original files.

- `POST /transfers`: `{transferId,targetDeviceId,routePreference?:"auto"|"lan"|"public"|"relay",files:[{fileId,name,size,mimeType,sha256}]}` → 201 `{transfer,replayed:false}`; identical replay → 200 with replayed true; differing reuse → 409. Omitted routePreference and explicit auto are the same canonical offer; changing it to another value requires a new transferId. IDs generated by client. Creation reserves global disk quota for all offered files, including zero-byte files.
- `GET /transfers` → `{transfers:Transfer[]}` active and retained own transfers.
- `GET /transfers/:transferId` → `{transfer}`.
- `POST /transfers/:transferId/accept`: `{fileIds:string[]}` → `{transfer}`. Receiver only; selected offered files become accepted, unselected offered files become rejected. Idempotent. Same-group automatic receiving is a client setting which submits this same authorization without an extra prompt; manual receiving preserves the per-file selection. Never reaccept rejected/canceled/expired files on replay. Upload is impossible until accepted. For a sender-constrained relay offer, accepted files immediately select transport=relay, so the sender need not wait for a route timeout.
- `PUT /transfers/:transferId/files/:fileId/chunks?offset=N`: raw `application/octet-stream`, at most chunkSize bytes. Sender only, accepted/uploading only. → `{file:TransferFile}`. Offset must equal committed offset, except an identical already-committed chunk replay succeeds. Gaps, overlaps with different bytes, and overflow → 409. Server commits offset only after file write is flushed. Client resumes by GET, never assumes failed HTTP means unwritten.
- `POST /transfers/:transferId/files/:fileId/complete`: `{}` → `{file}`. Sender only. Verifies exact size and streaming SHA-256 before atomically exposing ready file. Mismatch → 422, file becomes failed; other files unchanged. Repeated ready/received completes succeed. Zero-byte files still require acceptance and complete.
- `POST /transfers/:transferId/files/:fileId/retry`: `{attemptId:string}` → `{file}`. Sender only; accepted/uploading/failed only. Receiver's consent is retained; disk quota is rechecked, previous partial content removed, offset=0. Same attemptId retry is idempotent. Rejected/canceled/expired files cannot restart: make a new offer.
- `POST /transfers/:transferId/files/:fileId/cancel`: `{}` → `{file}`. Either participant; terminal ready/received files can be canceled explicitly. Removes temporary bytes and invalidates download tickets.
- `POST /transfers/:transferId/files/:fileId/download-ticket`: `{}` → `{ticket,expiresAt,downloadPath}`. Receiver only, ready/received only; 60-second single-use ticket. `downloadPath` is base-relative `/api/v1/downloads/<ticket>`, prepend configured base URL. Use browser navigation, no whole-file Blob. Browser handoff is NOT peer saved confirmation.
- `GET /downloads/:ticket` (ticket authorization) streams attachment without bearer; consumes ticket once, including GETs that later return 416. Without Range, returns the original complete file with 200. Supports one HTTP byte range: `Range: bytes=N-`, `bytes=N-M`, or `bytes=-suffixLength` → 206 with exact `Content-Range` and partial `Content-Length`; invalid, multiple, or unsatisfiable ranges → 416 with `Content-Range: bytes */size`. Zero-byte files support full GET only. Responses expose `Accept-Ranges: bytes` and strong `ETag: "sha256-<file.sha256>"`. `If-Range` equal to that ETag enables partial response; mismatched/unsupported validators ignore Range and return complete 200, so a client MUST truncate/restart rather than append. HEAD is unsupported (405) and does not consume the ticket. No ticket is logged.
- Download resume: retain the actual locally committed file length and stable file ID/hash; POST the existing `/download-ticket` for a **new ticket on every connection/retry**, then GET with `Range: bytes=<localOffset>-` and optional matching If-Range. Accept 206 only when Content-Range starts at that exact offset and total matches offered size. On 200 overwrite from byte 0; on 416 reconcile local size and verify the complete local hash or restart, never infer success from the error. A broken stream does not confirm receipt. Only after final local size/hash verification and atomic save may native receiver POST `/received`. Browser navigation remains the complete-file path and does not claim observable saved completion.
- `POST /transfers/:transferId/files/:fileId/received`: `{transport?:"relay"|"direct"}` → `{file}`. Default relay: receiver only, ready/received only. Direct: accepted with transport=direct → received without center bytes; frees relay reservation. Receiver must verify its final saved bytes before calling; browser must not auto-call on navigation. Relay receipt keeps bytes until TTL so user may download again. Direct-received files cannot issue relay download tickets.

Expired/revoked/canceled transfer access fails (410/403); background TTL cleanup frees reservation and bytes. App restart reconciles committed offsets by truncating uncommitted tails, fails files shorter than committed offset, and expires old files. Clients must reconcile before resuming.

### Route choices (center regression checks passed; native network acceptance remains separate)

The sender's offer routePreference is durable and immutable: **auto** lets the receiver apply its own receive preference; **lan** requires LAN-candidate direct transfer; **public** requires public-IP direct transfer; **relay** requires center relay. A non-auto sender choice overrides the receiver's local preference. In manual mode, a failure is shown for that path; clients must not silently switch categories. Retry the chosen path or create a new offer with another choice.

In auto mode, native receivers try LAN pull then LAN reverse push, followed by public pull/push and finally relay. Public cellular attempts require the relevant device's setting. Each phase has bounded connection attempts; merely seeing an address or matching a subnet is not proof of reachability. An IP behind NAT is not automatically a publicly reachable listener. The selected Android network carries both probe and file data. Center enforces the offered route constraint, but does not observe or attest the peer socket's actual physical routing.

`ROUTE_NOT_ALLOWED` (409) rejects direct-ticket/verification on relay-constrained offers, and rejects relay selection/chunks/complete/retry/download-ticket/download/relay-received on lan/public-constrained offers. The center keeps group authorization and peer pinning unchanged. These choices are stored in the existing transfers.offer JSON; no SQL table migration or schema version increase is needed. Old persisted offers have auto semantics, and omitted/explicit auto replays preserve their original canonical representation.

Clients without WebRTC support use the existing relay flow for auto/relay offers and must not silently accept a manual lan/public offer they cannot honor. WebRTC-capable clients may negotiate direct transfer when both devices advertise the requested scope. Browser download navigation remains a user action; automatic acceptance never means a file was saved on the device.

## Native peer authorization (additive v1 extension)

- `POST /devices/me/peer`: `{candidates:string[],certificatePem,certificateSha256}` → `{peer:{candidates,certificatePem,certificateSha256,expiresAt}}`. Online only, at most eight HTTPS origins (`https://host:port`, including bracketed IPv6). Center checks the current X509 certificate/fingerprint. Announcement expires after 30 minutes; refresh every two minutes is supported. An authenticated online device may replace its certificate and candidate list directly: there is no permanent certificate trust record, manual fingerprint step or re-enrollment requirement. Normal peer TLS pins the current center-announced certificate. Offline/expired metadata is deleted, not persisted in SQLite or returned to peers.
- Receiver `POST /transfers/:transferId/files/:fileId/direct-ticket`: `{}` → `{ticket,expiresAt,candidates,certificateSha256}`. Both participants must be online, file accepted with transport null/direct, and sender must have a current peer announcement. Sets transport=direct and emits transfer.updated. Already-selected relay → 409 PATH_SELECTED. Single-use authorization lasts 60 seconds and is invalidated when either participant goes offline.
- `POST /transfers/:transferId/files/:fileId/relay`: `{}` → `{file}`. Either participant, accepted/uploading only, subject to offer routePreference. Selects relay and invalidates pending direct tickets. Sender cannot override transport=direct (409 PATH_SELECTED); receiver in auto mode can fall back after both direct phases fail. New native senders wait for the receiver's explicit route choice instead of racing it with an eight-second relay timer. Browser may upload without this extra call for compatibility: first relay chunk selects relay when transport is null. No concurrent direct/relay upload.
- Sender `POST /direct-tickets/verify`: `{ticket,transferId,fileId}` → `{transferId,fileId,name,size,sha256,targetDeviceId,expiresAt}`. Requires sender's Bearer token; atomically consumes ticket. Expired, canceled, revoked or wrong-party tickets fail. Sender MUST call this before serving any file bytes and MUST map IDs to its own offered file references, never client-supplied paths.
- Peer candidate selection must pin the exact server-provided certificate SHA-256, reject redirects, have finite connect/application deadlines and use the same selected Android network for probe and data. No global certificate bypass. Ticket is sent only to the validated pinned peer. Receiver verifies length/hash, saves atomically, then POSTs `received {transport:"direct"}`. A failed direct attempt leaves file state available for retry; relay fallback is available only when the chosen route mode allows it.

Peer byte endpoint and network adapter implementation live in native client, not center. Declared center capability is not evidence of physical device direct reachability.

### Reverse HTTPS push

Peer registration accepts optional `push:boolean` and `cellularPush:boolean`; these are returned by `/devices`. Omitted means unsupported. The old pull endpoints and registration payload remain valid. `TransferFile` may add `directPush:{attemptId,scope:"lan"|"public",cellular,offset,state:"waiting"|"streaming"|"failed",expiresAt,error?}` while an attempt is active; file status remains `accepted` and transport remains `direct`. This negotiation is transient; file metadata and final receipt remain durable.

- Receiver `POST /transfers/:transferId/files/:fileId/direct-push`: `{attemptId,scope,cellular,offset}` → `{file}`. Requires an accepted file, both peers advertising push, no relay selection, a valid byte offset and a scope compatible with the offer. Cellular refers to the **sender's** network and requires its advertised permission. The receiver creates its local write slot before requesting push. Replaying an attempt is idempotent only with identical parameters.
- Sender `POST /transfers/:transferId/files/:fileId/push-ticket`: `{attemptId}` → `{ticket,expiresAt,candidates,certificateSha256,attemptId,scope,cellular,offset,size,sha256}`. Returns the receiver endpoint and a one-use, direction-bound ticket, valid at most 60 seconds before consumption.
- Receiver `POST /push-tickets/verify`: `{ticket,transferId,fileId,attemptId}` → `{transferId,fileId,attemptId,size,sha256,offset,scope,cellular,sourceDeviceId}`. Requires its own center bearer and atomically consumes the ticket. Pull verification rejects push tickets, and vice versa.
- Receiver `POST /transfers/:transferId/files/:fileId/direct-push/stop`: `{attemptId}` → `{}`. Invalidates only the matching attempt and its tickets. Sender `POST .../direct-push/fail`: `{attemptId,error}` → `{}` reports that matching attempt's failure; it does not choose relay.
- Native peer `PUT /push/:transferId/:fileId/:attemptId`: ticket in `X-GlobalSend-Ticket`, fixed `Content-Length=size-offset`, body is the remaining file bytes. The receiver verifies the center grant and exact active local slot before writing. Success returns `{bytes:size,attemptId}`. No center bearer is sent to a peer.

Only one local slot may write a file. Before changing direction, stage, or choosing relay, stop the old slot and await writer closure. Resume uses the same canonical `.part` location and short-lived SAF lease; it creates no second permanent copy. After streaming, the receiver closes the writer, checks full length/hash, renames, registers the saved file and submits the existing `received {transport:"direct"}`. Center `offset` remains zero for direct-only transfer. Manual LAN/public modes try both directions in that class without falling back to another class.

## WebRTC data-channel signaling (additive v1 extension)

The center exchanges authenticated signaling only; it never carries RTC file bytes. Both devices must advertise support, the receiver must already have accepted the file, and the receiver owns each route attempt. Existing native HTTPS endpoints and old client requests remain valid. All paths below are relative to `/api/v1`.

- `POST /devices/me/rtc`: `{scopes:["lan","public"]}` → `{rtc:{scopes,expiresAt}}`. Online only; scopes may be either subset, or `[]` to disable (returns `rtc:null`). Registration lasts 30 minutes; refresh every two minutes while connected. `GET /devices` adds optional `rtc` capability metadata only for online peers/self. A capability change notifies same-group devices with `devices.changed`.
- Receiver `POST /transfers/:transferId/files/:fileId/rtc`: `{attemptId,scope:"lan"|"public",offset}` → `{rtc:RtcView}`. Both current capabilities must include scope, offset must not exceed file size, file must be accepted with transport null/direct, and scope must match a manual sender choice. Selects transport=direct. Same attempt ID is idempotent only with identical scope/offset. A new attempt replaces the old attempt and invalidates all outstanding HTTPS pull/push grants for this file.
- Either participant `GET /transfers/:transferId/files/:fileId/rtc/:attemptId` → `{rtc:RtcView}`. Other devices, including nonparticipants in the same group, cannot read SDP or ICE. Ended/stale attempt returns `RTC_ENDED` (410).
- `POST .../rtc/:attemptId/description`: `{type:"offer"|"answer",sdp}` → `{rtc:RtcView}`. Receiver creates the offer; sender creates the answer after that offer. SDP must contain only application/data sections, never audio/video. Identical description retries are idempotent. No renegotiation within an attempt; start a new attempt instead.
- `POST .../rtc/:attemptId/candidate`: `{candidate,sdpMid:string|null,sdpMLineIndex:number|null}` → `{rtc:RtcView}`. Each candidate belongs to the authenticated role's list and is actually removed 30 minutes after its upload; repeating the identical candidate refreshes only that entry's deadline. SDP descriptions are also cleared after 30 minutes. A long-running streaming attempt may retain receipt/session metadata until the transfer deadline, **not its expired IPs**. No extra wire fields are required. Scope-aware ICE filtering and selected-pair verification belong to clients.
- Receiver `POST .../rtc/:attemptId/started`: `{}` → `{rtc:RtcView}`. Requires both descriptions. Negotiation expires after 60 seconds (or transfer expiry, if earlier); confirming the established connection extends the session to the transfer deadline.
- Either participant `POST .../rtc/:attemptId/fail`: `{error}` → `{rtc:RtcView}` records a failed attempt. It does not choose relay or authorize a new route.
- Receiver `POST .../rtc/:attemptId/stop`: `{}` → `{ok:true}`. Stops only that matching attempt; replaying an old stop cannot tear down its replacement. Native HTTPS selection, relay selection, cancellation, final direct receipt, expiry or device revocation also invalidate the RTC attempt.

`RtcView = {transferId,fileId,attemptId,sourceDeviceId,targetDeviceId,scope,offset,state:"negotiating"|"streaming"|"failed",expiresAt,error?,offer:null|{type:"offer",sdp},answer:null|{type:"answer",sdp},candidates:{source:IceCandidate[],target:IceCandidate[]}}`. `TransferFile.rtc` contains only `{attemptId,scope,offset,state,expiresAt,error?}` while active; it does not contain SDP or ICE.

Each signaling update sends ephemeral `{type:"rtc.changed",transferId,fileId,attemptId}` only to the two participants. Both must remain online for signaling and new HTTPS grants. Last-socket disconnect removes the related temporary attempt; its GET/signaling then returns `RTC_ENDED` (410), while a new direct request for an offline peer returns `DEVICE_OFFLINE` (409). SDP, ICE and notifications are never persisted in SQLite events and disappear on server restart. A surviving accepted file can negotiate a fresh attempt after reconnect without changing its identity, history or local partial.

The receiver must close the previous channel and await local writer closure before choosing another attempt or relay. Resume uses the same locally committed partial file. After completing and verifying its final bytes, receiver uses the existing `/received {transport:"direct"}`; center offset stays zero. A browser must not claim user download completion merely because it opened a save link.

`GET /info.rtc.iceServers` defaults to `[]` (host candidates only). Optional `STUN_URLS` is a comma- or whitespace-separated list of `stun:`/`stuns:` URLs, exposed as `[{urls:[...]}]`. No third-party STUN is selected by default. TURN URLs are not accepted: failed direct attempts use the existing explicit HTTPS relay policy instead of an additional hidden data relay.

## Foreground RTC reachability probes

`features.rtcProbes=true` enables dedicated short-lived data-only signaling, separate from file transfers. A probe never creates a transfer, file, relay allocation or durable history event. Both devices must be online, hold foreground leases and advertise the requested RTC scope; at least one must have platform `web`. The lexicographically smaller device ID initiates. Each device participates in at most one active probe. A probe expires after 12 seconds; the server cleans transient state every second and before probe requests.

- `POST /devices/me/rtc-probes/presence`: `{foreground:boolean}` → `{presence:{foreground,expiresAt:string|null}}`. Online only. `true` refreshes a 40-second foreground lease; clients refresh every 20 seconds. `false`, lease expiry or last-WS disconnect removes that device's active probe and recent results, without changing transfer/file state.
- `GET /devices/me/rtc-probes` → `{presence,peers,probes,results}`. `peers` contains only other same-group online foreground devices with a Web participant and shared RTC scopes: `{deviceId,scopes,foregroundExpiresAt}`. `probes` and `results` contain only this authenticated device's entries. An offline/background caller has no eligible peers.
- Initiator `POST /devices/:peerId/rtc-probes`: `{attemptId,scope:"lan"|"public"}` → `{probe:RtcProbeView}`. Same attempt/parameters retries reuse the active session. `PROBE_INITIATOR` identifies the wrong ordering; `PROBE_BACKGROUND`, `PROBE_BUSY`, `PROBE_UNAVAILABLE` and `RTC_UNAVAILABLE` are 409. Cross-group target is 403. A completed attempt ID cannot restart that probe.
- Either participant `GET /rtc-probes/:attemptId` → `{probe:RtcProbeView}`. Ended sessions return `PROBE_ENDED` (410).
- `POST .../description`: `{type:"offer"|"answer",sdp}` → `{probe}`. Initiator makes the offer, responder answers after the offer. Repeated identical descriptions are accepted; renegotiation uses a new attempt. Audio/video and TURN relay candidates are rejected.
- `POST .../candidate`: `{candidate,sdpMid:string|null,sdpMLineIndex:number|null}` → `{probe}`. Deduplicated into the authenticated role's array; no TURN relay candidates. Scope filtering and selected-pair checks use the same client rules as actual RTC transfers.
- Initiator `POST .../complete`: `{elapsedMs:number}` → `{result:RtcProbeResult}` after the data-channel nonce/echo succeeds. Requires both descriptions; elapsed time is 0–12000 milliseconds. Deletes the session and its address-bearing data immediately.
- Either participant `POST .../fail`: `{error:string}` → `{result}` with `success:false,elapsedMs:null`. Releases the session immediately so LAN failure can proceed to the public stage. Error is a short identifier, at most 128 characters.
- Either participant `DELETE /rtc-probes/:attemptId` → `{ok:true}`. Stops an active session without recording a reachability result. Completion/failure also ends the session, so a later GET returns 410; consume `results` in the snapshot rather than treating that as a second failure.

`RtcProbeView = {attemptId,initiatorDeviceId,responderDeviceId,scope,expiresAt,offer:null|{type:"offer",sdp},answer:null|{type:"answer",sdp},candidates:{initiator:IceCandidate[],responder:IceCandidate[]}}`.

`RtcProbeResult = {attemptId,initiatorDeviceId,responderDeviceId,scope,success:boolean,elapsedMs:number|null,checkedAt,expiresAt,error?:string}`. The latest result per pair/scope lasts two minutes. A 12-second timeout records `success:false,elapsedMs:null,error:"PROBE_TIMEOUT"`; foreground expiry/disconnect instead clears associated results. Results are transient observations, not file-transfer authorization or a guarantee of the next connection.

SDP/ICE/session/result changes send only `{type:"rtc.probes.changed"}` to the two participants. Foreground presence changes notify same-group online peers with that same type. Clients then fetch the snapshot. No addresses, SDP or nonce payloads enter SQL events. The data channel is `globalsend-probe-v1`: clients exchange bounded nonce/echo control messages, not file bytes; they close it promptly and start a fresh, receiver-consented RTC session for an actual file.

## Deployment and defaults

The same process and port provide API, WebSocket, file relay and the Web client. `WEB_ENABLED=true` (default) serves `<base>/app/` from `STATIC_DIR`; `WEB_ENABLED=false` disables only Web static routes and their landing redirect, even when static assets are absent. API, WebSocket, health and relay remain available. A deployment prefix is preserved on all routes: with `PUBLIC_BASE_URL=https://example.com/send`, use `/send/app/`, `/send/api/v1` and `/send/api/v1/ws`. The Web client uses its page's center by default; no separate relay address or production Web process is required.

Development binds loopback by default. Production requires `PUBLIC_BASE_URL=https://...[/prefix]`. New enrollment uses group passwords only; old bootstrap configuration is ignored and its compatibility Compose override is a no-op. Default file/text retention remains 24 hours and is independent of the 30-minute address lifetime. Other defaults: chunk 1 MiB, max file 2 GiB, relay quota 10 GiB, text length 100000, max active files per sender 64, disk reserve 64 MiB. Installer hosting remains disabled: `/globalsend/releases` and its children return 410.

Health outside API prefix: `<base>/health/live`, `<base>/health/ready`. Ready checks database and writable data/relay storage. Secret/ticket/auth headers and text bodies are excluded from logs. Persistence uses SQLite WAL and separate relay files; one server process only.
